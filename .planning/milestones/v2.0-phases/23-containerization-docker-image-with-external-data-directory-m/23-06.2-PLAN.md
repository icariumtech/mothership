<objective>
Address three remaining issues from the Phase 23 code review that harden the deployment without changing user-visible behavior on the homelab (where the docker-compose env vars are already correctly set):

1. **CR-02 (CRITICAL):** `config/settings.py` ships with `SECRET_KEY` falling back to a hardcoded insecure string and `DEBUG` defaulting to `True`. A container started directly from the image without the compose env vars (e.g. `docker run ghcr.io/.../mothership:latest`) would expose Django tracebacks containing the known fallback secret to anyone with port-8000 reachability.

2. **WR-04 (WARNING):** `ALLOWED_HOSTS` defaults to `'*'`, disabling Django Host-header validation entirely. With DEBUG=False (as docker-compose sets) this opens host-header injection attacks.

3. **WR-03 (WARNING):** `docker-compose.yml` has no healthcheck on `app`, and `mcp` uses `depends_on: app` without `condition: service_healthy`. The mcp container often races ahead of gunicorn startup and crashes its first httpx calls with connection errors.

Side effect: tightening settings.py forces `collectstatic` (which runs at Dockerfile BUILD time, not runtime) to also supply a SECRET_KEY. We provide one via a build ARG that has no runtime meaning.

Purpose: Make the image safe to run anywhere, not just under our specific compose file. Make the mcp service stop crash-looping on first boot. Keep all existing happy-path behavior intact (docker-compose.yml continues to pass real env vars).

Output: Hardened settings defaults, a working build-time SECRET_KEY plumbing, an app healthcheck, and an mcp dependency that waits for app readiness.
</objective>
