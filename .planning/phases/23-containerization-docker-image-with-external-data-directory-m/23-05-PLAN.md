  - "# Mothership GM Terminal — homelab deployment"
  - "# Before first run: touch db.sqlite3 (Docker creates bind-mount targets as directories if missing)"

Key implementation notes:
  - The mcp service command: ["python", "mcp_server.py"] overrides the CMD arg passed to docker-entrypoint.sh. The entrypoint's guard (if [ "$#" -gt 0 ]; then exec "$@"; fi) causes it to exec "python mcp_server.py" directly, bypassing migrate and createsuperuser. The app service handles DB initialization on startup.
  - DATA_DIR: "/app/data" must be set on both services — the Django DataLoader (via get_loader() and settings.DATA_DIR) reads from this path. Both services use the same mounted volume, so they see the same YAML files.
  - The mcp service does NOT need DJANGO_SUPERUSER_USERNAME/PASSWORD — it never runs the entrypoint's migration or superuser creation code.
  - Use "${VAR}" syntax (not $VAR) for env vars so docker compose validates they are set. "${VAR:-default}" provides a safe default for optional vars.

Create .github/workflows/docker-publish.yml. First ensure .github/workflows/ directory exists (create if absent).

Workflow structure:
  name: Build and publish Docker image

  on:
    push:
      branches: [main]
    workflow_dispatch:    — allows manual trigger from GitHub Actions UI (per Claude's Discretion)

  env:
    REGISTRY: ghcr.io
    IMAGE_NAME: ${{ github.repository }}

  jobs:
    build-and-push:
      runs-on: ubuntu-latest
      permissions:
        contents: read
        packages: write    — REQUIRED for pushing to GHCR; without this the login step will succeed but push will 403

      steps:
        - name: Checkout
          uses: actions/checkout@v4

        - name: Set up Docker Buildx
          uses: docker/setup-buildx-action@v3

        - name: Log in to GHCR
          uses: docker/login-action@v3
          with:
            registry: ${{ env.REGISTRY }}
            username: ${{ github.actor }}
            password: ${{ secrets.GITHUB_TOKEN }}

        - name: Extract metadata
          id: meta
          uses: docker/metadata-action@v5
          with:
            images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
            tags: |
              type=raw,value=latest,enable={{is_default_branch}}
              type=sha,prefix=sha-

        - name: Build and push
          uses: docker/build-push-action@v6
          with:
            context: .
            push: true
            tags: ${{ steps.meta.outputs.tags }}
            labels: ${{ steps.meta.outputs.labels }}
            cache-from: type=gha
            cache-to: type=gha,mode=max

Key notes:
  - secrets.GITHUB_TOKEN is auto-provided by GitHub Actions — no repository secret setup needed. It is scoped to the repository and granted packages:write by the permissions block.
  - cache-from/cache-to: type=gha uses GitHub Actions cache backend. This caches Docker build layers between runs, significantly reducing build time when only app code changes (Node and Python dependency layers are cached on first run).
  - The Dockerfile multi-stage build (Node stage → Python stage) works with docker/build-push-action out of the box — Buildx handles multi-stage builds natively.
  - workflow_dispatch allows a manual build trigger from the GitHub Actions tab without pushing to main (useful for testing the CI flow).
  - IMAGE_NAME: ${{ github.repository }} resolves to "owner/repo" format (e.g. "icariumtech/mothership"). Prefixed with REGISTRY (ghcr.io), the full image is ghcr.io/icariumtech/mothership.
  - Do NOT add any step for installing pnpm manually — the Dockerfile Node stage handles pnpm via "RUN corepack enable". The docker/build-push-action runs "docker build" which executes all Dockerfile RUN steps including corepack.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions runner → GHCR | GITHUB_TOKEN authenticates push; scoped to repository |
| homelab operator → docker-compose.yml | Operator supplies SECRET_KEY and DJANGO_SUPERUSER_PASSWORD via shell env; never committed |
| ./db.sqlite3 bind mount → container | Host filesystem file mapped into container; incorrect setup (missing file) causes Django error |

| T-23-05-02 | Information Disclosure | DJANGO_SUPERUSER_PASSWORD in docker-compose.yml | mitigate | Same shell env var pattern — not hardcoded; 2>/dev/null in entrypoint suppresses echo |
