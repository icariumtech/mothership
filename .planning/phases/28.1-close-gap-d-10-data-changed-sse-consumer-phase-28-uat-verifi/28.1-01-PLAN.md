<objective>
Close the D-10 gap from the v2.0 milestone audit. The backend already broadcasts `data-changed` SSE events from `core/views/gm_data.py` (lines 238, 279, 298, 356, 433, 625) after every GM-initiated write to the data directory, but the frontend `useSSE.ts` hook registers no listener for that event name, so players see stale data until they manually switch views.

Purpose: Make the GM-edits-YAML → player-terminal-auto-reloads E2E flow work end to end (the last broken integration in the v2.0 audit).

Output: An optional `onDataChanged` option in `useSSE`, a `data-changed` EventSource listener registered when that option is provided, and `SharedConsole.tsx` consuming it to re-fetch the active view payload (which transitively refreshes the currently-displayed map/ship/encounter data).
</objective>

registration only when the optional callback is provided, same console.error message shape.

<!-- Existing active-view fetch in SharedConsole.tsx -->
- `gmConsoleApi.getActiveView()` is the GM-side fetch (GMConsole.tsx line 53). On the player
  side the equivalent is `/api/active-view/` (the GET endpoint that `useSSE` is streaming from).
- The simplest reload path is: on `data-changed`, do a one-shot `fetch('/api/active-view/')`
  and feed the result through the same `handleViewChange` path that the existing SSE `onEvent`
  uses (lines 339-393). This refreshes encounter tokens, ship deck data, location data, etc.,
  in one round trip without per-view custom logic.

<!-- Backend payload shape -->

```
event: data-changed
data: {"path": "campaign/ships/icarium.yaml", "action": "write"}
```

`action` is one of: `write`, `patch`, `delete`, `list-append`, `svg-map-upload`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Django SSE stream → browser EventSource | Backend-originated events; no client-supplied payload reaches the listener. Trust source. |
| `/api/active-view/` GET → SharedConsole state | No GM authentication required (D-09); same trust posture as the existing `onEvent` SSE path. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-28.1-01 | Tampering | `data-changed` event payload (path/action) | accept | The new handler ignores payload fields entirely in v1 — it issues a blanket re-fetch. Even a malformed payload cannot redirect the fetch. |
| T-28.1-02 | Denial of Service | Burst of `data-changed` events triggering re-fetch storm | accept | Each `PUT /api/gm/data/` is GM-initiated (D-09 — single-user trust model); realistic burst is at most a handful per second. /api/active-view/ is cheap (file reads from disk per D-11). If observed in practice, add a 250ms debounce — out of scope for v1. |
| T-28.1-03 | Information Disclosure | Re-fetch exposes data to a non-GM client | accept | Per D-09, no auth on data API. Adding auth is a separate phase. The new path uses the same `/api/active-view/` endpoint the existing SSE consumer already calls — no new disclosure surface. |
</threat_model>
